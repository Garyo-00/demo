# 02. 安全指示事項（承認時入力）

> ステータス：ドラフト（**デモ未実装**・仕様のみ）／要レビュー
> 関連：[01-作業計画書テンプレート設定](./01-作業計画書テンプレート設定.md)（ブロックのON/OFF）、承認画面（未作成）

## 1. 概要
- 目的：元請が**承認するタイミング**で、その作業計画書に対する**安全指示事項**を記載できるようにする。
- 前提：テンプレート設定の**「安全指示事項」ブロックがON**のテンプレートで作成された作業計画書のみ対象。
  - **ON** … 承認画面に安全指示事項の入力欄が表示され、入力したうえで承認する。
  - **OFF** … 入力欄は表示されず、**ただ承認するだけ**。
- 利用ロール：**元請（承認フローで承認者に設定されたユーザー）**。職長・作業員は閲覧のみ。
- 単位：**1つの作業計画書に対して複数**。**作業内容ごと**に作る。
  「**作業内容＋安全指示事項**」を1かたまりとし、**承認者が任意の数だけ**追加して打ち込む。

## 2. 画面要素（承認画面内のセクション）

```
┌ 安全指示事項 ──────────────────────────── ＋ 追加 ┐
│  ┌ No.1 ────────────────────────────── 🗑 ┐      │
│  │ 作業内容   [ 桁上げ作業（作業内容1）      ▼ ]  │      │
│  │ 安全指示事項                                  │      │
│  │ [ 吊り荷下に立ち入らないよう合図者を専任し… ]  │      │
│  │ 最終更新：2026/08/06 10:12 元請 田中           │      │
│  └────────────────────────────────────┘      │
│  ┌ No.2 ────────────────────────────── 🗑 ┐      │
│  │ …                                             │      │
│  └────────────────────────────────────┘      │
└──────────────────────────────────────────────┘
        [ 否認 ]  [ 承認 ]
```

- セクション見出し「安全指示事項」＋右上「＋ 追加」。
- かたまり（カード）ごとに：**作業内容**／**安全指示事項**／最終更新者・更新日時／削除。
- 並べ替え（ドラッグ）対応（想定。テンプレート設定の項目テーブルと同じ操作感）。

## 3. 表示項目 / 入力項目

| 項目 | 形式 | 必須 | 初期値・データソース |
|---|---|---|---|
| 作業内容 | プルダウン選択（＋自由入力の補足） | ⚠️ | **その作業計画書に入力済みの「作業内容」から選択**（想定）。同じ作業内容に複数の指示を紐づけることも可（想定）。 |
| 安全指示事項 | 自由入力（複数行） | ⚠️ | 空 |
| 最終更新者／更新日時 | 表示のみ | — | 保存時に自動記録 |

- [ ] ⚠️ 「作業内容」は**計画書の作業内容から選択**で良いか（自由入力のみ／選択＋自由入力の併用も可）。
- [ ] ⚠️ かたまりの**上限数**（無制限で良いか）。
- [ ] ⚠️ 安全指示事項の**文字数上限**、定型文（よく使う指示）のマスタ登録・呼び出しの要否。

## 4. 機能・操作

| 操作 | 内容 | ロール |
|---|---|---|
| ＋追加 | かたまりを1つ追加（任意の数） | 承認者 |
| 編集 | 作業内容・安全指示事項を入力／修正 | 承認者 |
| 削除 | かたまりを削除（確認ダイアログ） | 承認者 |
| 並べ替え | ドラッグで順序変更 | 承認者 |
| 承認 | 入力内容を確定し、計画書を承認済にする | 承認者 |
| 否認・差戻し | 計画書を職長に戻す | 承認者 |

- **承認ユーザーが複数いる場合、他のユーザーが登録した内容を上書きできる**（本要件）。
  - 承認フローが多段（例：職長→工事担当→所長）の場合、**各段階の承認者が同じ安全指示事項を編集・上書きできる**（想定）。
  - 上書きの際、**誰がいつ書いたか**を必ず表示し、無言で消えたように見えないようにする（§7）。
- [ ] ⚠️ **最終承認後**の編集可否（推奨：**承認後は編集不可**とし、修正が必要なら差戻し→再承認。承認済の内容が現場に出た後に黙って変わるのを防ぐため）。

## 5. 状態・ロール別表示差

| 状態 | 承認者（元請） | 職長 | 作業員（QR閲覧） |
|---|---|---|---|
| 承認前（ブロックON） | 入力・編集・削除 可 | 閲覧のみ（⚠️ 承認前に見せるか） | 非表示（承認済のみ公開） |
| 承認前（ブロックOFF） | セクション非表示（承認のみ） | — | — |
| 承認済 | 閲覧（⚠️ 編集不可を推奨） | 閲覧 | **閲覧可**（計画書と一緒に表示） |

- [ ] ⚠️ 承認前の入力内容を職長に見せるか（差戻し時に指示だけ先に見せたい場合がある）。
- [ ] ⚠️ 点検QRからの閲覧時、安全指示事項をどこに表示するか（計画書本文の該当作業内容の直下／末尾にまとめて）。
- [ ] ⚠️ チェックリスト実施画面でも安全指示事項を表示するか。

## 6. データ・外部連携

データ構造（想定）:

```jsonc
// 作業計画書
{
  "id": "plan001",
  "templateId": "tplCrane",
  "blocks": { "safetyInstruction": true },   // テンプレートから引き継ぎ
  "workItems": [ { "id": "w1", "name": "桁上げ作業" }, ... ],
  "safetyInstructions": [
    {
      "id": "si1",
      "order": 1,
      "workItemId": "w1",        // 作業内容への参照
      "text": "吊り荷下に立ち入らないよう…",
      "updatedBy": "u_tanaka",
      "updatedAt": "2026-08-06T10:12:00+09:00",
      "version": 3               // 楽観ロック用（§7）
    }
  ],
  "safetyInstructionsVersion": 7 // セクション全体の版（追加・削除・並べ替え検知用）
}
```

- 出力帳票・点検QR閲覧の双方に渡る項目のため、[README §6.5](./README.md) の帳票仕様と合わせて確定が必要。
- [ ] ⚠️ 参照している作業内容が後から削除・変更された場合の整合（推奨：`workItemId` 参照が切れたら「作業内容（削除済）」と表示し、指示自体は残す）。

## 7. 同時編集の衝突回避（**推奨方式**）

> 前提：本要件は「**他の承認者の内容を上書きできる**」こと。したがって**編集をロックして締め出す方式（悲観ロック）は採らない**。
> 目的は「上書きを禁じること」ではなく、**気づかないうちに上書きされること（lost update）を無くすこと**。

### 7.1 採用を推奨する方式（3点セット）

**① 楽観ロック（バージョン照合）— 必須**
- クライアントは編集開始時点の `version` を保持し、保存時に一緒に送る。
- サーバは現在の `version` と照合し、**一致すれば保存して version+1**、**不一致なら 409 を返す**（保存はしない）。
- 409 のときは画面に「**他の承認者が先に更新しました**」と表示し、**相手の内容／自分の入力内容を並べて提示**したうえで、
  - **［相手の内容で上書きする］**（自分の入力を反映）
  - **［最新を取り込む］**（自分の入力を破棄して読み直す）
  - **［両方残す］**（自分の入力を新しいかたまりとして追加）
  を**承認者が明示的に選ぶ**。→ 上書きは可能、ただし**必ず気づいたうえで行われる**。
- 照合の粒度は**かたまり単位（`safetyInstructions[].version`）＋セクション全体（`safetyInstructionsVersion`）**の2段構え。
  別々のかたまりを触っている限り衝突しないため、実運用でぶつかる頻度を大きく下げられる。

**② 編集中プレゼンス表示（ソフトロック）— 推奨**
- 承認画面を開いている間、30秒間隔でハートビートを送り、**「〇〇さんが編集中」**をセクション見出しに表示（2分で失効）。
- **入力自体はブロックしない**（上書き可の要件を尊重）。「先に声を掛ける」ための予防表示。

**③ 変更履歴の保持 — 推奨**
- 上書き前の内容を版として保存し、**誰が・いつ・どこを変えたか**を履歴として参照・復元できるようにする。
- 現場の安全指示は責任の所在が重要なため、**「最後に書いた人」だけでなく「途中で消えた指示」も追える**ようにしておく。

### 7.2 併せて決めておくこと
- 保存タイミング：**明示保存（承認ボタン／保存ボタン）を基本**とし、自動保存する場合は**下書き**として扱う（推奨：入力中の自動保存は下書き、承認時に確定）。
- 否認・差戻し時に、入力済みの安全指示事項を**保持する**（推奨。再承認時に書き直す手間を避ける）。

### 7.3 採らない方式と理由
| 方式 | 不採用の理由 |
|---|---|
| 悲観ロック（編集中は他ユーザー編集不可） | 「他ユーザーの内容を上書きできる」要件に反する。承認者が離席したまま握り続ける事故も起きる。 |
| 何もせず後勝ち（last-write-wins のみ） | 先に書いた指示が**無言で消える**。安全指示の性質上、許容できない。 |
| 自動マージ（テキストを機械的に結合） | 安全指示の意味が壊れる恐れがある。人が選ぶ（①）方が安全。 |

- [ ] ⚠️ 上記 ①②③ の採用可否。②③ を初期リリースで見送る場合、**①（楽観ロック）は最低限必須**。
- [ ] ⚠️ 履歴の保持期間・表示場所（承認画面内／別途の変更履歴画面）。

## 8. 例外・エッジケース
- [ ] ⚠️ 承認者が**安全指示事項を1件も入力せずに承認**できるか（推奨：**任意（0件でも承認可）**。ただし0件のまま承認しようとしたら確認ダイアログを出す）。
- [ ] ⚠️ テンプレートのブロック設定を**後から**ON/OFFした場合、作成済み計画書への影響（推奨：**作成時点のテンプレート内容を計画書にスナップショット**して固定。[README §6.3](./README.md)）。
- [ ] ⚠️ 作業内容が0件の計画書で「作業内容ごと」をどう扱うか（推奨：作業内容の選択を空のまま指示のみ登録可）。
- [ ] ⚠️ 承認済み計画書を職長が編集して再申請した場合、既存の安全指示事項を引き継ぐか。
- [ ] ⚠️ 承認者が入力中に、職長が計画書本体を編集した場合の整合。

## ⚠️ 9. 未決事項・考慮不足（要確認）
- [ ] ⚠️ 多段承認のとき、**どの段階の承認者が入力できるか**（全段階／最終承認者のみ）。
- [ ] ⚠️ 安全指示事項の**必須化**をテンプレート側で切り替えたいか（「ONかつ必須」「ONだが任意」）。
- [ ] ⚠️ 定型文マスタ（現場でよく使う指示の登録・呼び出し）の要否。
- [ ] ⚠️ 作業員が閲覧した／読んだことの記録（既読・チェックリストへの組み込み）の要否。
- [ ] ⚠️ 上書き発生時の通知（先に書いた承認者へ知らせるか）。
